如果你正在用 Claude，不需要因为政治争论或工具热度而仓促关闭账户。先保住资料，再移走一项任务，最后决定要不要换主力工具。 你拥有合法使用权的项目应该能被另一个人和另一套工具接手。

你不必公开上传任何聊天文件。 站内迁移路线选择器只输出一个通用执行计划，不读取个人数据，也不会把你的对话上传到网站。先用它生成计划，再按官方教程手工导出。




02｜先明确：迁移的终点不是“下载成功”


一个 AI 账号里至少有七种资产：对话、记忆、项目说明、原始上传文件、生成成品、代码/脚本、自动化与连接配置。官方导出不一定包含全部。真正的完成标准是 资料独立保存、关键文件可打开、至少一项工作在替代环境重做成功。


需要迁移的人通常分为四类：个人账户仍能登录；Team/Enterprise 组织成员；团队所有者；账号已无法登录。先确定自己属于哪一种，不要照抄别人的菜单。


不必今天把所有历史都搬完


给重要资料按风险分组：


    

  • P0：当前收费项目、客户授权材料、正在运行的自动化和唯一原件。
    • 

  • P1：常用提示词、背景资料、项目决定、已产出文件。
    • 

  • P2：过期聊天、闲聊、已有其他备份的材料。
    • 



从一项 P0 项目开始。重要的是可恢复，不是立刻清空旧账号。


03｜第 1 步：申请官方导出，保存原件


根据 Claude 官方导出说明，个人 Free、Pro、Max、Ultra 等计划的账号，可在 Claude 网页版或桌面端进入 Settings → Privacy → Export data。官方说明 iOS/Android 不能直接发起该导出；组织成员可能需要 Owner 或 Primary Owner 开启权限；Primary Owner 使用组织数据与隐私入口。


官方邮件下载链接通常 24 小时后过期，可能只能使用一次，下载时还须登录。把下载的压缩包放入 00-official-export/YYYY-MM-DD/，不要立刻解压后删除原件。文件名要保留日期、平台、账户或组织类别；切忌把账号口令写进文件名。


官方明确：聊天导出不包含原来上传的文件，也不包含某些独立产品数据。 因此要单独补齐项目文件、原稿和成品。官方也表示个人账户之间不能直接导入导出的聊天作为完整迁移。


一步验收


能说出导出日期、原压缩包位置、是否能成功解压、里面实际包含哪些内容；不能只写“已导出”。


04｜第 2 步：建立七类资产目录


建议使用以下结构，普通用户可以在文件管理器手动建立，不需要先装开发工具：


AI-Migration/
├── 00-official-export/      # 平台提供的原始导出
├── 01-conversations/        # 可检索对话与索引
├── 02-memory/               # 人工审核后的记忆与偏好
├── 03-projects/             # 项目背景、决策、任务说明
├── 04-original-files/       # 自己上传过的原始附件
├── 05-deliverables/         # 可编辑成品及版本
├── 06-code-and-workflows/   # 源码、自动化定义、提示词
└── 07-restore-check/        # 恢复测试与差异记录



把 templates/migration-inventory.csv 填成真实台账：项目名、原始系统、资料类别、当前路径、可否导出、保存位置、保密等级、最近抽查和缺口。任何一栏不知道就填写“未知”，不要写“已完成”。


05｜第 3 步：记忆要单独迁，不要复制整段私人历史


Claude 已提供 Memory import/export 官方说明，但不同产品和版本的入口、自动整理能力有所区别。先按自己的账号中当前实际可见的设置进行操作，再人工检查。


推荐在本地保存 02-memory/profile.md：


# 工作偏好（教学模板）
职业角色：
正在进行的项目：
长期目标：
写作风格：
反复被纠正的问题：
常用软件与技术栈：
不得自动执行的事情：
最近一次人工复核日期：



隐私排除： 删去账号密码、API Key、家庭成员敏感资料、医疗记录、客户名单、内部财务数据；只有确实需要并获得授权的信息，才带入新工具。记忆是提示系统理解背景，不是可恢复资产的唯一证据。


06｜第 4 步：逐个项目写“交接卡”


每个正在使用的项目独立保存一份 PROJECT-HANDOFF.md。内容包含目标、实际输入、关键限制、做过的取舍、最后可用结果、尚未完成的工作、验收标准和下一步。


最小交接卡范例：


项目：门店内容生产（教学化匿名示例）
目标：每周产出可审查的真实维修知识短内容
已有输入：获得授权的原始采访、产品信息、照片
核心限制：不虚构客户故事、故障结论或营业数据
当前进度：已有脚本结构，是否发布与播放结果待核对
下一步：用另一工具生成一条脚本并对照原稿人工验收
验收：技术事实可核查，镜头有来源，文件可编辑



它能让下一位协作者接手，也能让你从 Claude 切换至其他模型时不靠“把旧聊天全部喂过去”这种高成本办法。


07｜第 5 步：原文件、代码与成品分开保存


原来上传的图片、PDF、Word、设计稿、视频，应该从你最初保存的位置补回；不要误以为聊天导出包一定保留这些二进制文件。生成的图表、汇报、代码、合同草稿等，要保存 可编辑源文件 + 最终成品 + 版本日期。


如果是本地代码项目，先检查 Git 提交、未提交修改、.env 文件和部署配置。代码仓库只推送允许公开的内容；密钥、客户资料和数据库备份应存放在受控私有位置。


对于懂命令行的人


本地检查单个文件 SHA-256：


shasum -a 256 important-file.zip



Windows PowerShell：


Get-FileHash .\important-file.zip -Algorithm SHA256



比对哈希可以证明两个文件字节相同，但不能证明内容完整或没有错误；仍要实测解压、打开和恢复。


08｜Claude Code 是单独的一类迁移，不能只导出聊天


对于在 VS Code、终端或桌面端使用 Claude Code 的读者，建议额外保存 Git 仓库、未提交改动、项目规则 CLAUDE.md、Skills、MCP 配置说明、Hooks 行为、依赖与测试命令。~/.claude/settings.json 是用户级配置，.claude/settings.json 是项目共享配置，.claude/settings.local.json 通常用于个人局部设置；授权凭据、Token 等不能随意复制到公开项目。以官方设置文件说明为准。


从 Claude Code 的交互会话里使用 /export 可保存该会话的纯文本记录；这不是针对所有项目、所有本地文件的全量导出，也不能保证被另一产品直接导入。真正可移植的项目上下文建议写进 PORTABLE-PROJECT.md，再分别按 Codex/Gemini CLI 等要求提供适配文件。


只迁一项任务的做法： 在另一个 Agent 打开同一份 Git 源码 → 读取项目说明 → 修改一个明确的 UI / 代码问题 → 运行测试 → 产出 diff 和截图 → 人工复核。不要因为打开了文件夹就宣布 Agent 迁移完成。


打开 Claude Code 专项迁移手册与三个可编辑模板。




09｜第 6 步：只迁一个真实任务，做双轨试验


从最简单的任务开始：写一页产品 FAQ、整理一份公开资料表、改一处网页或恢复一个项目提示词。保持输入相同、成品格式相同、验收标准相同，记录新工具是否需要人工改写。

10｜第 7 步：独立恢复，才算交付


从另一个文件夹、另一台设备或第二份独立备份中打开核心文件，不依赖旧账号聊天窗口。完成下面的最小恢复：


    

  1. 找到官方原始导出，并确认能解压。
    2. 

  2. 抽查最早、最近和一条长对话。
    3. 

  3. 找出项目交接卡和原始上传文件。
    4. 

  4. 用新工具完成一项真实任务。
    5. 

  5. 逐项核对数据、排版、引用、脚本执行或网页打开。
    6. 

  6. 写下失败与补救，确定谁负责下次复测。
    7. 



“导出成功”与“迁移完成”不是同一状态。 只有当前这项工作恢复通过，才记录“该任务已迁移”；不要一项成功就把全部项目标记完成。

12｜Andy 的实践札记：跨工作台，应该保存什么


真实作者工作流，非客户迁移成功率声明。 我同时使用 ChatGPT、Codex、WorkBuddy 等 AI 工具做内容、开源项目与产品工作。反复切换时，最大的摩擦不只是“某个模型记不记得我”，而是同一个项目的目标、迭代记录、源码和可交付文件散落在多个应用里。


因此我强调把重要项目的 需求、决策、版本、可编辑文件和验收条件 固化为独立文档。跨工具持续备份这项工作仍需要定期验证，不能因为设置了自动任务就宣称所有数据都已经安全恢复。这也是本手册把恢复测试写成最后一步的原因。


作为一个公开内容案例，“修车阿江” 的工作不是凭空写上“AI 能自动经营汽修店”，而是围绕真实故障知识、采访内容和脚本结构整理可交付的素材。迁移演练可以拿一条已有原稿，换工具生成多平台版本，再由懂维修的人审核。这里没有声称已经由迁移带来流量或成交增长。


13｜七天完成最小迁移


Day 1： 申请并下载导出；标明账号和日期。

Day 2： 按七类目录整理；写资产台账。

Day 3： 清理记忆；写 P0 项目交接卡。

Day 4： 补齐原文件、源代码和成品。

Day 5： 选择一个可以使用的新工具；重做同题任务。

Day 6： 从独立备份恢复，记录失败。

Day 7： 修正缺口，建立定期复查和责任人。


14｜谁来做、谁复核


个人用户可一人完成；小团队建议至少有资料负责人、业务验收人、账号/权限负责人。这些角色可以兼任，但迁移状态必须留下具体日期和证据。对于受保密义务约束的客户资料，先取得必要授权，公开仓库只放无隐私的结构模板。
